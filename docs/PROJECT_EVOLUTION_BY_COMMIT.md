## 2. 项目定位与当前形态

PhotoLib 是面向摄影团队的图片工作站，围绕“项目立项—需求发布—多人接单—图片上传与处理—采用统计—工时确认—数据导出”形成业务闭环。

当前系统采用前后端一体化交付：

- 前端：React 19、TypeScript、Vite、Ant Design、Axios。
- 后端：Java 21、Spring Boot、Spring Security、MyBatis-Plus。
- 数据：MySQL + Flyway，当前迁移脚本为 V1–V6。
- 存储：本地磁盘或阿里云 OSS，可在启动时校准照片记录与对象存储。
- 交付：前端构建产物打入后端 JAR，浏览器使用 Hash Router。
- 质量保障：后端单元/集成测试、前端 ESLint、全流程 QA 脚本和多轮测试报告。

## 3. 功能开发主线

项目演进可归纳为八个阶段：

1. **需求建模**：先建立流程图、帮助文档和 API 契约，再根据产品决策补齐批量上传、保留策略等规则。
2. **核心后端**：一次性落地认证、用户、校区、项目、需求、照片、采用、工时、统计、导出、通知和审计等领域能力。
3. **前端与本地开发闭环**：实现主要业务页面，并增加本地对象存储，使开发环境不依赖 OSS。
4. **部署一体化**：补充 README、OSS/Linux 部署说明，将前端打入 JAR 并切换 Hash Router。
5. **测试与品牌化**：建设测试计划、自动化脚本和服务测试；增加可配置品牌名称、Logo、主题色等后台能力。
6. **兼容与稳定性**：修正测试编译、空值边界、lint 和路由问题，并提供旧 PhotoWarehouse 数据迁移。
7. **图片基础设施增强**：提升图片压缩质量，增加数据库与对象存储的自动校准。
8. **消息体系与权限修复**：从站内通知扩展到广播、定向消息、富文本和图片，再修复授权错误映射与采用状态显示。

## 6. 典型功能的开发流程

从提交历史可以归纳出项目实际采用的开发闭环：

1. **契约先行**：在 `API.md` 中确认资源、状态、权限与限制。
2. **数据库迁移**：涉及持久化的功能先增加 Flyway 脚本，保持环境可重复升级。
3. **后端纵向实现**：实体/Mapper → Service → Controller → 安全配置或基础设施。
4. **前端接入**：补充类型、API 调用、路由、页面和样式，形成用户可操作流程。
5. **自动化验证**：增加服务单测、控制器测试或外部集成测试；外部依赖通过显式开关保护。
6. **文档与复测**：更新测试计划、结果、部署或迁移文档。
7. **分支合并**：通过 PR 合入 `master`，合并提交仅作为交付节点。
8. **线上问题回补**：以小型修复提交处理权限、路由、显示或质量问题，并增加回归测试。

消息功能是这一流程最完整的例子：V5 建表与后端服务 → 前端通知入口 → 服务测试 → V6 扩展管理消息/图片 → 富文本列表与详情页 → 控制器测试 → PR 合并 → 权限异常回归修复。

## 7. 当前维护关注点

- **本地工作区不是干净状态**：后续切换分支、变基或批量修改前，应先确认 `PhotosPage.tsx` 及未跟踪报告的归属。
- **README 中文显示需核对编码**：当前 PowerShell 默认读取时出现乱码迹象，建议统一确认文件为 UTF-8，并检查终端编码后再决定是否修改文件。
- **提交粒度前期偏大**：首个后端提交覆盖 100 余个文件，后续追责和回滚成本较高；建议未来按数据库、后端、前端、测试拆分为可独立验证的提交。
- **合并历史存在重复展示**：统计功能量时应采用非合并提交或首父历史，不能把 PR 合并提交的 diff 再计一次。
- **外部集成需分层测试**：OSS、DirectMail、旧 PostgreSQL 等测试应保持显式启用，普通 CI 使用替身或本地实现。
- **数据库迁移只增不改**：已发布的 V1–V6 不应直接修改，后续结构变化使用 V7 及更高版本。

## 8. 后续建议

1. 为每个新功能采用“需求/API → Flyway → 后端 → 前端 → 测试 → 文档”的统一 PR 模板。
2. 在 CI 中固定执行 `npm run lint`、前端构建和后端测试，将 OSS 等真实集成测试设为手动或受保护任务。
3. 补充一张当前系统架构图，并把 API、部署、迁移、测试文档从 README 建立索引。
4. 对认证、消息、图片存储和旧库迁移做一次端到端验收，确认分支合并后的组合行为。
5. 整理或忽略 `.idea/`、`.claude/` 等本地工具目录，避免误提交个人环境配置。
